# WHOIS Pattern Refresh System Design

## Overview

An automated system to keep WHOIS parsing templates current by periodically querying live servers, detecting drift in parsed output, and publishing updated template packs independently of the NuGet package. Part of the v4.0 update.

## Goals

1. Maintain a canonical registry of domains to query, with research context
2. Automatically refresh sample WHOIS responses on a weekly cadence
3. Detect parsing breakages (no match, field regression) and surface them via a rolling PR
4. Normalise template and sample directory structures to a consistent convention
5. Publish versioned, signed template releases that clients can download and cache
6. Expose both automatic and manual template update paths in the library

## Non-Goals (Deferred)

- Tokenizer v3 template optimisation (follow-on work after infrastructure is stable)
- Cross-referencing with weppos/whois Ruby library for coverage gaps (evaluate after bootstrapping)
- Auto-fixing broken templates (requires human or AI agent intervention)
- Client-side template validation (covered by the pipeline's drift detection before release)

## 1. Domain Registry

**File:** `tools/WhoisRefresh/domains.jsonc`

Hand-curated, committed to the repo, reviewed via PRs. This is the source of truth for what gets queried.

```jsonc
{
  "servers": {
    "whois.nic.uk": {
      // UK registry, Nominet. Rate limit: ~10 queries/min.
      // Thick WHOIS - returns full registrant data.
      "tld": "uk",
      "domains": {
        // google.co.uk: exercises multi-nameserver, DNSSEC fields
        "found": ["google.co.uk", "bbc.co.uk"],
        "not-found": ["thisdoesnotexist.co.uk"]
      }
    },
    "whois.denic.de": {
      // DENIC requires whitelisted IP for full queries.
      // Samples are static, sourced from weppos/whois Ruby library.
      "tld": "de",
      "static": true,
      "domains": {
        "found": ["google.de"],
        "not-found": ["thisdoesnotexist.de"]
      }
    },
    "whois.verisign-grs.com": {
      // Verisign shared infrastructure - shares rate limits with ccwhois.verisign-grs.com
      "tld": "com",
      "rateGroup": "verisign",
      "domains": {
        "found": ["google.com"],
        "not-found": ["thisdoesnotexist.com"]
      }
    },
    "ccwhois.verisign-grs.com": {
      // Shares rate limits with whois.verisign-grs.com
      "tld": "cc",
      "rateGroup": "verisign",
      "domains": {
        "found": ["example.cc"],
        "not-found": ["thisdoesnotexist.cc"]
      }
    }
  }
}
```

### Fields

- **`tld`** — the TLD this server is authoritative for
- **`static`** — when `true`, the refresh tool skips querying this server. Samples are maintained manually. Applied by a human after investigating persistent query failures.
- **`rateGroup`** — optional. Servers in the same rate group share infrastructure and are queried sequentially (same 5-second delay rules), while different groups run in parallel.
- **`domains`** — keyed by expected status (`found`, `not-found`, `throttled`, `reserved`, etc.). Each key is an array of domain names to query.
- **Comments** — standardised format aimed at developers and AI agents. Include: server quirks (rate limits, encoding, access restrictions), why specific domains were chosen (exercises particular format variants), known format history.

### Domain Name Validation

Domain names in `domains.jsonc` are validated on load. Any domain containing path separators (`/`, `\`) or path traversal sequences (`..`) is rejected with an error.

### Bootstrapping

The initial `domains.jsonc` is generated by extracting domains from the existing ~756 sample files in `tests/Whois.Tests/Samples/`. For servers that can't be queried live (e.g. `.de` requiring IP whitelisting), samples are sourced from the weppos/whois Ruby library and the server is marked `static: true`.

### Static Server Detection

1. First run assumes all servers are queryable (no `static` flag)
2. Refresh tool records failures in `refresh-results.json` with error type
3. If a server fails consistently across 3+ weekly runs, the drift PR includes a note suggesting it be marked static
4. A human reviews and applies `"static": true` with a comment explaining why

### Status Mismatch Handling

If a domain listed under a given status key returns a response that parses to a different status (e.g. a domain under `"found"` returns `not-found`), this is flagged as drift in the drift report. The sample is saved to the directory matching the *actual* parsed status. The drift report notes the mismatch (e.g. "google.co.uk: expected found, got not-found") so a human can update `domains.jsonc`.

## 2. Directory Structure

### Templates (Embedded Resources)

```
src/Whois/Resources/{server}/{tld}/{status}/{nn}.txt
```

Examples:
```
src/Whois/Resources/whois.nic.uk/uk/found/01.txt
src/Whois/Resources/whois.nic.uk/uk/found/02.txt
src/Whois/Resources/whois.nic.uk/uk/not-found/01.txt
```

- All lowercase, kebab-case status names
- Sequential numbering (`01.txt`, `02.txt`) for multiple format variants per status
- Template front matter `name:` follows the path convention (e.g. `whois.nic.uk/uk/found/01`)

### Samples (Test Fixtures)

```
tests/Whois.Tests/Samples/{server}/{tld}/{status}/{domain}.txt
```

Examples:
```
tests/Whois.Tests/Samples/whois.nic.uk/uk/found/google.co.uk.txt
tests/Whois.Tests/Samples/whois.nic.uk/uk/not-found/thisdoesnotexist.co.uk.txt
```

- Domain name as filename — self-documenting, deterministic for refresh

### Migration

- Scripted rename from current structure (not manual)
- `ResourceReader` updated to enumerate `{server}/{tld}/{status}/*.txt`
- `WhoisParser` template loading updated for the new depth level
- All parsing tests updated for new `SampleReader` paths
- All tests must pass after migration before any other changes

## 3. Refresh Tool

**Location:** `tools/WhoisRefresh/` — a .NET console app added to `Whois.sln`.

**Dependencies:**
- Project reference to `src/Whois/` (for `WhoisParser`, template matching)
- `Spectre.Console` / `Spectre.Cli` (CLI framework + rich output)
- `Microsoft.Extensions.Logging` (consistent with main library)

### Commands

#### `refresh`

Queries live WHOIS servers and saves responses.

- Reads `domains.jsonc`, validates domain names (rejects path separators and traversal sequences)
- Skips servers with `static: true`
- Parallel across different servers/rate groups, sequential within a server and within a rate group (5-second delay between queries)
- **Max concurrency:** unbounded across rate groups (I/O-bound TCP work)
- **Per-query timeout:** 30 seconds
- **Max response size:** 64KB per query (WHOIS responses are typically < 10KB)
- Saves raw responses to the samples directory
- Parses each response using the library's `WhoisParser`
- Writes `refresh-results.json`
- Prunes entries for domains removed from `domains.jsonc`

#### `detect`

Compares current parse results against a previous baseline.

- Reads current and previous `refresh-results.json`
- Classifies changes:
  - **No match** — sample doesn't match any template → breakage
  - **Field regression** — fewer extracted fields than baseline → breakage
  - **Template shift** — different template matches but field coverage equal or better → info, logged but not alerted
  - **Status mismatch** — actual parsed status differs from expected status in `domains.jsonc` → drift, logged
- For breakages, includes a summary of raw response differences (first 50 divergent lines between previous and current response)
- Generates `drift-report.json` (structured diff) and `drift-report.md` (rendered markdown)
- If breakages found: creates or updates a single rolling PR on the `template-drift` branch
  - PR includes updated sample files
  - PR description contains structured drift report table
  - If the `template-drift` branch has commits not in `main` (human is working on it), creates a new branch (`template-drift/YYYY-MM-DD`) instead to avoid overwriting human work
  - If an existing drift PR is open and has no human commits, updates it (no duplicates)

### Console Output

**Local (human) usage:**
- Spectre.Console progress table during refresh (server name, status, domains queried)
- Colour-coded drift report (green = ok, yellow = template shift, red = breakage)
- Summary table (X servers queried, Y breakages, Z new samples)

**CI (GitHub Actions):**
- Detects CI environment via `GITHUB_ACTIONS` env var
- Plain text output (no Spectre progress bars)
- GitHub annotations mapped by severity:
  - `::error::` — breakages (no match, field regression)
  - `::warning::` — persistent server failures, status mismatches
  - `::notice::` — template shifts, informational changes

### Output Artifacts

- **`refresh-results.json`** — per-sample: timestamp, matched template, list of extracted field names, error info. Generated, not committed.
- **`drift-report.json`** — structured diff against baseline. Generated.
- **`drift-report.md`** — rendered markdown for PR body. Generated.

## 4. Drift Detection Workflow

The end-to-end workflow for resolving drift:

1. **Weekly refresh runs** → queries servers, parses responses, compares against baseline
2. **Breakage detected** → rolling PR created/updated on `template-drift` branch with structured drift report
3. **Human or AI agent picks up the PR** → investigates format changes using the drift report data (including raw response diffs), `domains.jsonc` comments, and sample content
4. **Template fixed** → updated/new template added, refresh tool run locally to verify
5. **PR submitted/updated** → CI validates all samples parse correctly
6. **PR merged to main** → triggers template release workflow

## 5. Template Release Pipeline

### Release Artifact

- A `.zip` containing all templates in the normalised `{server}/{tld}/{status}/{nn}.txt` structure
- Estimated size: < 1MB compressed
- A `manifest.json` inside with:
  - Version (CalVer: `2026.07.12.1`, sequence suffix for same-day releases)
  - Content hash (computed over template files only, before manifest is generated)
  - Template count
  - Per-template list with individual hashes
- A detached `.sig` file for signature verification

### Signing

- **Algorithm:** Ed25519 via minisign
- **Public key:** Embedded as a constant in the library source code, compiled into the NuGet package. This is the trust anchor.
- **Signing key:** Stored as a GitHub Environment secret in the `template-release` protected environment (with required reviewers), not a repo-level secret.
- **Key rotation:** Requires a new NuGet package version shipping the new public key. Old clients on older NuGet versions will reject packs signed with the new key — this is acceptable and desirable (key rotation is a high-severity event; consumers should actively upgrade).

### Changelog

Each release includes:
- **`changelog.json`** — machine-readable structured diff (source of truth)
- **`changelog.md`** — rendered markdown, used as the GitHub release body

Content: which servers changed, templates added/removed/modified, fields affected. Generated by diffing the per-template hashes in the current and previous `manifest.json` files (not from git history or drift reports). This approach avoids a git dependency in the packaging tool while still capturing manual template edits, since the manifest reflects actual file content regardless of how it changed.

### Publishing Flow

1. PR merged to `main` with changes in `src/Whois/Resources/**`
2. GitHub Action triggers (in `template-release` protected environment)
3. Builds template zip + `manifest.json`
4. Signs artifact with minisign (using Environment secret)
5. Computes CalVer version (queries existing GitHub releases for sequence number)
6. Creates GitHub release with changelog as body
7. Attaches zip + sig as release assets

## 6. Client-Side Template Updates

### Three Consumption Patterns

1. **Default** — embedded templates only, no network calls, works everywhere
2. **Auto-update (opt-in)** — lazy check on first use, graceful degradation
3. **Manual update** — consumer calls `UpdateTemplatesAsync()`, full control

### Template Resolution Order

Templates are lazy-loaded per server on first lookup (existing `WhoisParser` behaviour). When loading templates for a server:

1. Check cached template pack for that server's templates
2. If cached version exists and is valid (signature verified) → use cached
3. Otherwise → use embedded templates (always available as fallback)

Servers already loaded in the current process keep their templates. If a new pack is downloaded mid-process (via auto-update or manual update), it is cached to disk and takes effect for any server not yet queried in this process.

### Auto-Update Behaviour

Enabled via `WhoisOptions.AutoUpdateTemplates = true` (default: `false`).

**Check timing:**
- Triggered on first `WhoisLookup` call per process lifetime (lazy)
- Fully async, does not block the query — uses currently loaded templates while check runs
- Respects throttle/backoff timestamps before making any network call

**Throttle/backoff:**
- On success: don't check again for a configurable interval (default: 24 hours)
- On failure: exponential backoff — 1 hour → 4 hours → 24 hours → 7 days (capped)
- Backoff state persisted in cache directory (small JSON file alongside template pack)
- On app restart: honour existing backoff state, don't reset
- If backoff state file is corrupt or has implausible values, reset to defaults

**Failure handling:**
- Network failure → log warning via `ILogger` (see Logging section below), continue with current templates
- Disk write failure → log warning once ("auto-update enabled but cache directory is not writable — automatic updates will be disabled for this session"), disable auto-update for process lifetime. No repeated attempts, no repeated warnings.
- Signature verification failure → log warning, discard downloaded pack, continue with current templates
- Never throw from the update path

**Download and verification sequence:**
1. Download zip to a temp file
2. Verify detached signature against the raw zip bytes using the compiled-in public key
3. Only then extract — during extraction, reject entries with `..` or absolute paths, cap total uncompressed size
4. On successful extraction, delete the previous cached pack (keep at most one cached pack)
5. If deletion of old pack fails, log warning and continue

**HTTP client hardening:**
- HTTPS only — reject non-HTTPS URLs
- Default TLS verification (never disable)
- Limit redirect count to 5 (default .NET `HttpClient` allows 50)
- Reject template packs older than the currently loaded version (prevents downgrade attacks)

**Custom URL warning:**
- If `TemplateReleaseUrl` is set to a non-default value, log a warning at startup: "Using custom template release URL"

### Manual Update

`WhoisLookup.UpdateTemplatesAsync(CancellationToken)` — available regardless of auto-update setting.

Returns a result indicating: success (new version applied), already up to date, or failure (with reason). Consumer handles errors as they see fit. New templates take effect for any server not yet queried in this process.

### Cache Directory Security

- Create cache directory with restrictive permissions (user-only: 0700 on Unix, ACL-restricted on Windows)
- Use atomic write pattern (write to temp file, rename)
- Verify cache path is not a symlink before writing

### Template Status

`WhoisLookup.TemplateStatus` — a read-only property exposing:
- `CurrentVersion` — the template pack version in use (or "embedded" if using built-in)
- `Source` — `Embedded` or `Cached`
- `LastCheckTime` — when the last update check occurred (null if never)
- `NextCheckTime` — when the next check is eligible (null if auto-update disabled)
- `LastError` — the last update error (null if none)
- `AutoUpdateEnabled` — whether auto-update is active (may be `false` even if configured, e.g. after disk failure)

### Logging

All auto-update log entries use structured fields via `ILogger` message templates:

- **Network failure:** `"Template update check failed for {TemplateUpdateUrl}, attempted version {AttemptedVersion}, HTTP status {HttpStatus}, current version {CurrentVersion}"` — `Warning` level
- **Disk failure:** `"Auto-update disabled: cache directory {CacheDirectory} is not writable — {ErrorType}: {ErrorMessage}"` — `Warning` level
- **Signature failure:** `"Template pack signature verification failed for {TemplateUpdateUrl}, version {AttemptedVersion} — discarding pack"` — `Warning` level
- **Success:** `"Template pack updated from {PreviousVersion} to {NewVersion} via {TemplateUpdateUrl}"` — `Information` level
- **Skipped (backoff):** `"Template update check skipped, next eligible at {NextCheckTime}, last error: {LastErrorReason}"` — `Debug` level
- **Skipped (throttle):** `"Template update check skipped, last checked {LastCheckTime}, next eligible at {NextCheckTime}"` — `Debug` level

### Configuration

Via `WhoisOptions`:
- `AutoUpdateTemplates` — `bool`, default `false`
- `TemplateCacheDirectory` — `string?`, default: platform-appropriate app data folder
- `TemplateUpdateCheckInterval` — `TimeSpan`, default: 24 hours
- `TemplateReleaseUrl` — `string?`, default: this repo's GitHub releases API URL. HTTPS only.

## 7. GitHub Action Workflows

### Weekly Refresh (`whois-refresh.yml`)

**Trigger:** Cron (weekly, Sunday 02:00 UTC) + `workflow_dispatch` for manual runs.

**Timeout:** 30 minutes.

**Steps:**
1. Checkout repo
2. `dotnet run --project tools/WhoisRefresh -- refresh`
3. `dotnet run --project tools/WhoisRefresh -- detect`
4. If breakages found: create/update rolling drift PR on `template-drift` branch
5. If no breakages but samples changed: commit updated samples + baseline to a branch

**Failure handling:**
- If `refresh` succeeds but `detect` fails → don't commit anything, workflow fails visibly
- If all queries fail → don't update baseline, workflow fails
- Partial success (some servers fail) → commit results for successful servers, note failures in drift report
- **Staleness alert:** if `refresh-results.json` baseline is older than 4 weeks (no successful run in a month), the workflow opens a GitHub issue flagging the staleness

**Permissions:** `pull-requests: write` scope on `GITHUB_TOKEN` for branch creation and PR management.

### Template Release (`whois-template-release.yml`)

**Trigger:** Push to `main` when `src/Whois/Resources/**` files changed.

**Environment:** `template-release` (protected, with required reviewers).

**Steps:**
1. Checkout repo
2. Build template zip + manifest
3. Sign artifact with minisign (using Environment secret)
4. Compute CalVer version (query existing releases for sequence)
5. Create GitHub release with changelog body
6. Attach zip + sig as release assets

**Permissions:** `contents: write` scope on `GITHUB_TOKEN` for releases. Signing key in Environment secret.

## 8. Refresh Results Baseline

**File:** `refresh-results.json` — generated by the refresh tool, committed to the repo as the comparison baseline for drift detection.

```json
{
  "version": "2026-07-12T02:00:00Z",
  "results": {
    "whois.nic.uk": {
      "uk": {
        "found": {
          "google.co.uk": {
            "timestamp": "2026-07-12T02:01:15Z",
            "matchedTemplate": "whois.nic.uk/uk/found/01",
            "extractedFields": ["DomainName", "Registrar", "CreatedDate", "ExpiryDate", "NameServers", "Status"],
            "error": null
          }
        }
      }
    }
  }
}
```

### Error Schema

When a query fails, the `error` field contains:

```json
"error": {
  "type": "ConnectionRefused | Timeout | RateLimited | AccessDenied | ParseFailure | Unknown",
  "message": "Connection refused",
  "detail": "whois.denic.de:43"
}
```

The `type` enum enables automated analysis — e.g., `AccessDenied` and `ConnectionRefused` across 3+ runs supports the static server suggestion logic.

The baseline is updated each successful refresh run and committed. Drift detection always compares the current run against the last committed baseline. Entries for domains removed from `domains.jsonc` are pruned on each refresh run.

## 9. Testing Strategy

### Refresh Tool (`tools/WhoisRefresh.Tests/`)

- **Network abstraction:** queries use `ITcpReader` (already exists in the library), allowing test doubles for deterministic WHOIS responses
- **JSONC parsing:** unit tests for `domains.jsonc` loading, validation (domain name validation, `static` flag handling, `rateGroup` grouping)
- **Rate group sequencing:** verify servers in the same `rateGroup` are queried sequentially while different groups run in parallel
- **File I/O:** file system operations abstracted for testability — verify samples saved to correct paths, response size cap enforced
- **Partial failure:** tests for scenarios where some servers succeed and others fail

### Drift Detection

Unit tests with crafted `refresh-results.json` baselines and current results:

- **No match:** sample that previously matched a template now matches nothing → classified as breakage
- **Field regression:** sample matches a template but produces fewer fields → classified as breakage
- **Template shift:** different template matches with equal or better fields → classified as info
- **Status mismatch:** actual status differs from expected status in registry → classified as drift
- **Boundary cases:** same field count but different fields, baseline missing, empty results, first run with no previous baseline

### Directory Migration

The migration script includes verification assertions:

1. **File count:** total files before = total files after
2. **Content integrity:** SHA-256 hash of every file's content unchanged (only paths changed)
3. **Resource resolution:** all embedded resource names resolve correctly after the path depth change
4. **Test pass:** all existing parsing tests pass after migration

### Client-Side Template Updates

- **Mock HTTP:** `HttpClient` abstracted via `HttpMessageHandler` for testing all download paths (success, network failure, HTTP errors, redirect limits, HTTPS enforcement)
- **Mock file system:** cache directory operations abstracted for testing disk write failures, permission errors, symlink detection
- **Signature verification:** test fixtures for valid, tampered, missing, and expired signatures. Verify that extraction only occurs after successful verification.
- **Downgrade prevention:** test that a pack older than the current version is rejected
- **Backoff logic:** unit tests for exponential backoff calculation, state persistence, corrupt state recovery
- **Lazy loading integration:** verify that cached templates are used for servers not yet queried, and embedded templates are used for servers already loaded
- **Template status property:** verify `TemplateStatus` reflects correct state through all lifecycle stages

### GitHub Actions

- Refresh and detect commands are independently testable outside of Actions (CLI tool, no GitHub dependency)
- PR creation/update logic abstracted behind an interface (testable with mocks, uses `gh` CLI or GitHub API in production)
- Workflow files validated via `actionlint` in CI

1. **Tokenizer v3 template optimisation** — modernise template syntax (front matter settings, simplified DateTime tokens) after the refresh infrastructure is stable and can catch regressions

3. **AI agent integration** — the drift PR structure is designed to be consumable by AI agents, but automated fix-and-submit is out of scope for this phase
